## Question

What is the cloud part of an extension, and which of today's features need one?

The slot list (its resolution is on that ticket) found that comments, presence, shares, team history and the viewer have code on spool.page, so they cannot become extensions with only window, frame and daemon parts. Settle:

- Which features have cloud code today and what it does (spool-cloud, `~/dev/projects/spool-cloud`).
- Whether those features become extensions with a cloud part, or stay core for now and reach the cloud through core services.
- What a cloud part may do: records, realtime channels, audience and authorisation, migrations, version compatibility with older daemons.
- Official only, or ever open to others (it runs on spool.page's servers).
- How the deck uses it: following a presenter by link, playing a deck in the cloud viewer, which pins its own spool version.

## Resolution (task 557, 2026-11-10)

Liam picked take A: **no extension code runs on spool.page. The cloud is platform.**

- Comments, presence, shares, team history and the viewer keep their cloud code as part of spool.page, as sync is. Their UI in the app (the comments pane, pin tool and layer, the presence layer, the history pane) becomes extensions that reach the cloud through SDK services any extension may use (`team.comments`, `team.presence`, `team.history`, shares), so there is still no private back door.
- An extension has **four parts, not five**: window, frame, daemon, compile. `cloud` leaves the manifest.
- New extensions get one generic service from the cloud: a **live channel**, small ephemeral messages to everyone on a project or on one share link. Share-scoped channels are separate from team presence, which must never reach link viewers. Generic extension records in the cloud are a later door, not v1: the deck does not need them.
- **Following a presenter by link** rides a share-scoped live channel: one authorised publisher, anyone holding the link may subscribe without an account, latest state on join and reconnect, carrying page, frame and step only. Expiry and a lapsed team end it. This is new work on spool.page (link viewers get settled HTTP only today).
- **Owned data gets a sharing rule.** The manifest's data entries take `share: "never"`; `notes.md` uses it so speaker notes are never served to share viewers. Settling and filtering must keep extension metadata and drop such files.
- Comments' orchestration, about 840 lines inside the sync object, is pulled into a module of its own in the sync rework (same Durable Object, scoped tables and dispatch). That is cleanup inside the platform, not an extension host.
- spool.page pins a spool version (0.48.0 today) and is bumped by hand, so an official extension's frame part, compile part and play mode reach the cloud viewer only when the pin moves. The build order takes "the cloud follows each spool release, gated by its tests".
- Turned down: a cloud part for official extensions (a server-side host designed for one or two users) and for anyone (strangers' code on our servers).
