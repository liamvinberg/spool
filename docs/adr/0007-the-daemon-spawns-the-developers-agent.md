# The daemon spawns the developer's agent

Spool's honest self-description changes here. It was "opening an untrusted design is inert". It becomes "spool can run an agent with write access to your repo, and that agent asks before it writes outside `design/`" (#114, #191).

This does not breach the boundary [issue #41](https://github.com/liamvinberg/spool/issues/41) drew. #41 names the CLI and daemon as the trusted computing base and forbids project code from spawning processes; that is why terminal frames are still a static disabled surface ([ADR-0006](./0006-terminal-frames-run-real-processes.md)). An agent chat is the other side of the same line: the daemon spawns it, on a control-plane route behind the control capability, because the hands explicitly asked for a turn. No frame, no player document, no project file and no shared design can reach it.

**What is spawned.** The developer's own `claude`, resolved by bare name off `PATH`, as a child of the daemon inheriting its environment. It reuses whatever CLI login is already on the machine — `apiKeySource: "none"` in all seven captures under `fixtures/captures/` is that claim's evidence. Spool configures no key, asks for none, and stores none. It also strips none: someone's own CLI configured with a key breaks no promise spool made.

**How the fence is expressed.** Three arguments, and they are the whole of it (`src/daemon/agent-spawn.ts`):

- `--setting-sources user`. Only the developer's own settings load. The project's stay out, because a project's `allow` list can make its own dangerous calls quiet, and opening somebody's design must not change what your agent may do. Measured on 2.1.220: a throwaway project whose `.claude/settings.json` registers a `SessionStart` hook fires two hooks under this spawn, all of them the developer's own, and three the moment `project` is added to the sources. The measured cost is that the project's `CLAUDE.md` and `AGENTS.md` go with the settings; spool pays it in the appended system prompt, one line of which spends the agent's own read on that file.
- `--permission-mode default`, set explicitly rather than left to the machine. Measured on 2.1.220, a default spawn inherits the user's `defaultMode`, and a `bypassPermissions` there ran a spool-spawned agent with every check off, everywhere on disk.
- One allow rule, `Edit(./design/**)`, and nothing denied. Deny beats allow and cannot express an exception, so the fence is a list of what is quiet rather than a wall with a door. `Write(path)` rules are inert for file permission checks; `Edit` covers every file-editing tool. Work outside `design/` asks once and is never blocked.

**The ask is not wired yet.** Approvals arrive as data only when `--permission-prompt-tool stdio` is passed, and answering one needs a person, so both belong to the ticket that builds the rail. Until then the fence holds in its strict direction — a write outside `design/` does not happen — but the agent meets a refusal rather than a question, and stops. The allow rule and the mode are what make that boundary real; the channel that carries the question to a human is the next piece.

Tools are not narrowed and the shell stays open. Measured: with writes denied the agent immediately routed around it through Bash, and the binary already fences the shell by path unaided. A command allowlist buys prompts, not safety.

**What rides along with eyes open.** The developer's skills, slash commands, custom agents, hooks, connectors and personal memory. Hooks are arbitrary shell commands running because spool pressed a button, and there is no lever that keeps connectors and drops hooks — it is the same switch. The hermetic alternative was argued and lost on the product rather than the security: a designer pulling design tokens from a connector into spool is the difference between a canvas and a toy, and inheriting means spool never owns an abstraction over connectors.

**No permission grant outlives the thread that made it.** "Always" is held with the running thread and written to no file, so a click inside a design tool never changes what the developer's terminal agent may do tomorrow.

**The spawn is injectable** (`src/daemon/agent-exec.ts`), mirroring the terminal executor already on the daemon app's options. Its fixture implementation replays a capture line by line, so CI never spawns an agent, never touches a login, and never depends on a model.

**Amended 2026-07-30/31: approvals guard file mutations, and nothing else.** Dogfooding made the fence noisy — every shell command, web search and out-of-project read asked, and a prompt on a harmless tool teaches a person to click approve without reading. The allow list widens to the tools that cannot change anything (`Read(//**)`, `WebFetch`, `WebSearch`) and to the whole shell (`Bash`): no command ever asks. The shell's fence is the OS instead of a question — the binary's sandbox rides the same `--settings` (`sandbox.enabled`), Seatbelt confines every sandboxed command and its children to writes under the project root and the session temp dir — but the sandbox is containment, not an approval mechanism, and the two claims were measured apart on 2.1.220. Containment holds: a parent-directory write is refused, and narrowing the boundary to `design/` is not expressible (`denyWrite` on the root with `allowWrite` on `design/` blocks `design/` too, deny beating allow in the filesystem rules as in the permission rules). Auto-allow does not: in `--print` with no prompt tool sandboxed commands ran unprompted, but with the stdio prompt tool wired a sandboxed read-only loop still asked (observed live 2026-07-31) — so the bare `Bash` rule is the only floor that holds on both paths, including the binary's own unsandboxed retry of a command the sandbox broke. Spool's own CLI is excluded from the sandbox outright (`excludedCommands`), because `spool shot` launches Chrome and Chrome cannot start under Seatbelt (mach port permission denied, observed live); the verbs are read-only by construction (#6). The accepted trade — any shell write is silent where the same change through `Edit` would ask — is carried by the framing, which routes changes outside `design/` through the file tools, where the one surviving ask lives. Session evidence for the widening: across every designer session in the dogfood projects, the shell ran `spool`, `cd`, `cat`, `grep`, `sed`, `echo`, loops, `ls`, `mkdir`, `curl` — nothing an approval would have caught, and every ask was answered allow. The edit rule is built absolute per spawn (`Edit(//<root>/design/**)`), because a relative rule anchors to the shell's current directory rather than the spawn's: `cd` persists across the agent's Bash calls, so after one `cd design` the relative rule matched nothing and every frame write asked — observed live 2026-07-31 and reproduced in a probe, with the absolute form immune.

**Amended 2026-09-06: engine ownership.** The installed binary, inherited settings, authentication and process-per-turn decisions above describe the Claude Code integration. The daemon now routes through an engine boundary while keeping the existing Claude translator and permission mapping. Each thread keeps its engine and an exact model-session reference separately from its saved rail picture. Legacy records belong to Claude Code and retain their original resume identity; a missing engine or model session leaves saved history readable. The daemon owns live turns, so a departing viewer does not stop work, and a restart never resumes it automatically. The boundary also permits an engine to own managed login and report an applied permission mode; bundled credentials, runtime supervision and enforcement belong to the bundled integration.


**Amended 2026-09-06: bundled engine ownership.** The `spool` engine bundles pi 0.85.1 and starts one lazy host supervised by the daemon. The installed-binary and no-credentials claims above continue to describe Claude Code. Bundled connections belong to Spool: the host serializes credential updates and logout through one canonical store, saves atomically in instance-owned state, and reports failed saves. Its directories are private (0700), its credential and session files are private (0600), and account status never returns stored credentials. The host receives a restricted environment and a separate empty home; it imports neither ambient provider accounts nor repository settings or executable key resolvers.

The host supplies its own resource loader, Spool framing and skill. Project instructions enter as text. Pi extensions, hooks, packages, prompts, themes and settings are never discovered. Default tools are disabled; file and command access must be explicitly wrapped by their authorization integrations before being exposed.

Each bundled thread resolves its daemon-owned session reference to one exact instance-owned snapshot. The host restores that file's entries into the SDK session manager, checkpoints messages atomically, and saves before disposing an idle session. It never searches for a recent conversation. A viewer reconnect reads the daemon's held turn; a host crash settles active turns without replay and a later user turn can start a fresh host against the saved session. The rail picture remains independently readable.

**Amended 2026-10-08: the person's own agents, and no bundled engine (#363).** The bundled `spool` engine is removed, with its host, credential store, managed login, command runner, catalog and sandbox, and the `@earendil-works/pi-*` and `@anthropic-ai/sandbox-runtime` dependencies. Spool ships no agent and holds no credential; every engine is an agent the person installed, resolved by bare name off `PATH`, signed in through that agent's own terminal flow, and spawned with the daemon's environment. The amendment above on bundled engine ownership no longer describes anything that runs. Threads the bundled engine left behind keep it as a read-only owner: their rail picture stays readable, and the daemon refuses to start, probe or continue them.

The engines are Claude Code, as above, and pi, with Codex joining by the same boundary (#362). Pi is the person's own `pi --mode rpc`, one process per turn like Claude Code: spool appends its framing with `--append-system-prompt` and loads nothing else of its own, so the person's pi settings, extensions, skills and context files all ride along, for the reason connectors and hooks do above. The first turn names the session with the thread's id (`--session-id`); pi answers `get_state` with the exact file it wrote, the daemon keeps that file per thread in its own state (`pi-sessions.json`), and every later turn opens that file and no other (`--session`). A thread is continuable while that file exists. The offer is read live from a throwaway process that opens no session (`--no-session`): `get_available_models`, then each model's own thinking levels, which persists nothing because RPC model changes are never saved as defaults. Pi has no approvals and no permission modes, so its offer says so and the rail draws no mode menu; the fence above is Claude Code's, and on pi the framing alone routes changes outside `design/` through the file tools. An extension's own dialog is declined where it arrives, so a turn never waits on a question nobody sees. Stop is pi's own `abort`, and a turn ends on `agent_settled`, pi's "no remaining automatic work".

The rail's wall lists an install line per agent and looks again on Check again and on window focus. The Mac app bundles no engine.

**Amended 2026-10-09: spool's designer rides every engine (#367).** Each engine's turn spawn carries one thing of spool's own beyond its framing: a `designer` sub-agent, written from spool's state (`<spoolDir>/designer/`, rewritten only when its text changes) and named on the command line, so nothing lands in the project, `~/.claude`, `~/.codex` or `~/.pi`. Claude Code takes it as `--agents <file>`, a custom agent its own `Agent` tool runs. Codex takes it as an agent role, `-c agents.designer.config_file=<file>` and `-c agents.designer.description=…`, whose config layer carries the designer's instructions; the spawn tool shows the description. Pi has no sub-agents, so the designer is a pi extension loaded with `-e <file>`: a `designer` tool that runs a child `pi --mode json -p --no-session` on the parent's model and thinking level with the designer's prompt appended, and reports each tool the child starts as the call's progress. This narrows "loads nothing else of its own" above to "nothing else but the designer". Probes carry no designer. Each engine's fan-out reads as the rail's delegation, the `Agent` call Claude Code makes, with a task under it that starts, steps and lands; the framing gains one line telling the main agent to give each direction its own designer and make single edits itself. Recorded in `fixtures/captures/*-designers.json`.

**Amended 2026-10-09: Codex, and settings that belong to the machine (#361, #362).** Codex is the person's own `codex app-server`, one JSON-RPC process per turn like the others, resolved off `PATH` and spawned with the daemon's environment. Spool never sets `CODEX_HOME`, because that is where the person's login and config live, and it writes nothing into `~/.codex`. A Codex older than 0.151.0 counts as not installed, so it is never picked as the fallback engine; the engine reports it as outdated besides, so the menu and the wall say it needs updating, with its update line, rather than offering to install it. Spool's three modes map onto Codex's own approval policy and sandbox, each pair confirmed by the `thread/start` echo in the recorded sessions: Ask first is `untrusted` with `workspace-write`, Auto-edit is `on-request` with `workspace-write`, and Full access is `never` with `danger-full-access`. The fence's two quiet cases carry over as answers, not rules: spool itself accepts a file change whose every path is inside `design/` and a command that is exactly one read-only `spool` verb, and every other approval Codex asks for reaches the rail. "Always" is Codex's `acceptForSession`, which dies with the turn's process, so the engine holds the allowed scope in memory per thread and answers the same ask itself on that thread's later turns. It is still written to no file. Codex mints its own thread id, so spool keeps the exact reference per thread, as it does pi's session file. Both now live in one store in spool's state, `sessions/<engine>.json`, which replaces `pi-sessions.json` and `codex/threads/`; the old files are still read, so earlier threads keep continuing.

Two of Codex's own defaults cut against this ADR, and each is settled differently. The first is trust. Codex writes `[projects."<root>"] trust_level = "trusted"` into the person's `~/.codex/config.toml` when a `thread/start` names a `cwd` in a project that has no trust entry, under a sandbox that can write there. The first build blocked that write by passing the project as trusted on the spawn (`-c projects={…={trust_level="trusted"}}`). A trusted project loads the repo's own `.codex/config.toml`, so opening somebody's design could change what your agent may do, which is what `--setting-sources user` exists to prevent for Claude Code above. It also overrode a person's own `untrusted` entry. That flag is gone. A turn's `thread/start` now names no `cwd`, so Codex takes the process's directory, the project root, and writes nothing (verified on 0.161.0). The project's trust stays whatever the person set: with no entry, Codex reads AGENTS.md and keeps the repo's `.codex/` layer off. The second is network, and that trade is accepted. `workspace-write` blocks loopback too, and every `spool` verb talks to the daemon on localhost. So under Ask first and Auto-edit the spawn turns on `sandbox_workspace_write.network_access`, which opens all network from inside the sandbox. Codex 0.161 has no loopback-only switch: its per-domain allowlist is a proxy profile that a `thread/start` naming a sandbox cannot use, and Node's `fetch` doesn't read the proxy anyway. Network was never part of Claude Code's fence above either, whose shell and web tools are already allowed.

Spool's framing reaches Codex as the thread's `developerInstructions` on `thread/start` and `thread/resume`. Codex holds one developer instructions value and the last one set wins, so the turn first reads the person's own (`config/read`) and sends theirs followed by spool's. AGENTS.md and Codex's base instructions are separate and untouched. The designer role's own instructions still replace the person's inside a designer, which is Codex's role layer.

Agent, model, effort per engine and permission mode are no longer per project. They are one machine-wide choice in spool's state (`agent-defaults.ts`), so a new project starts on the agent and mode last used on this machine, and opening somebody's design still can't change either. A one-time migration took the most recently opened project's values from `registry.json`. The registry's per-project settings scope, which no setting used afterwards, is removed.

The menu's words for the modes follow what runs rather than the other way round. Claude Code's bare `Bash` rule above and Codex's `on-request` both run a command inside the agent's sandbox without asking, so the asking modes promise to ask only before commands outside it: Ask first "Asks before it edits outside design/ or runs commands outside its sandbox.", Auto-edit "Edits files without asking. Asks before commands outside its sandbox.", and Full access "Never asks."
