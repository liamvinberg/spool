# Figma: design documents, executable Make apps, and code workflows

Research date: 2026-09-05. Scope: Figma Design, its prototype player, Dev Mode and MCP, ordinary Figma Make, and the separately gated Make local-codebase beta. Figma Sites is included only where its code layers provide contrary evidence to a product-wide runtime claim. This is part of [spool-cloud #58](https://github.com/liamvinberg/spool-cloud/issues/58).

**The consequential finding is that “Figma cannot run live applications” is false at product level.** Design's native prototype system operates on design nodes, interactions, and variables. Make has editable application code, backends, and web publishing. Make can also play inside a Design canvas. A closed beta goes further and edits an existing local repository while displaying its running application. These are different workflows with different ownership and availability constraints, not one undifferentiated capability. Sources and qualifications follow.

**Observed:** this Free account completed a native Design navigation prototype and a separate Make app with a real textarea, React state and save counter. Direct code changes updated Make's preview; a visual font edit produced a reviewed source diff through Apply. Backend persistence, arbitrary network access and existing-repository editing remain documentary or unverified here.

## Evidence and surface boundaries

**Observed** means the session's sole desktop operator performed the action on this Mac; the hands-on section records outcomes and screenshots. **Documented** means a current first-party help page, API reference, or explicitly identified vendor announcement supports the claim. **Inferred** identifies the interpretation drawn from those facts. **Unverified** identifies a capability or experience this pass did not establish. Vendor demonstrations and claims are not hands-on observations. Documentation may describe a rollout unavailable to this account. No claims here establish representative user behavior, measured performance, or comparative usability.

The earlier [Figma editing workflows](../figma-editing-workflows.md) contains the detailed small-edit shortcut matrix and responsive-card lesson. This report extends that work into lifecycle, reuse, execution, ownership, agents, and collaboration. The [shared-library study](../shared-library-second-pass.md) remains useful historical Spool context; its recommendations are not findings of this competitor study.

## 2. Visual editing and layout

**Documented:** Design's layout is a native auto-layout system. Horizontal and vertical flows, wrapping, grid, sizing modes and constraints are more precise descriptions than “flexbox.” Some properties map to CSS concepts, but the document remains Figma's model. The API exposes `FIXED`, `HUG`, `FILL`, explicit min/max dimensions, paints, and layout fields. **Inferred:** familiar terminology or exported CSS does not establish browser-layout equivalence for all cases. [REST node types](https://developers.figma.com/docs/rest-api/file-node-types/)

| Scenario | Documented editing behavior | What to inspect in a walkthrough |
| --- | --- | --- |
| Responsive card/list | Shift+A adds auto layout. Flows can be switched; changing content or adding/removing children adjusts their layout. Horizontal flow supports wrap. [Auto layout guide](https://help.figma.com/hc/en-us/articles/360040451373-Explore-auto-layout-properties) | Longer text should test the text's own sizing and its parent's behavior together, not just the outer width. |
| Grid layout | Grid has tracks, cells, spans, auto-positioning, fractional Fill tracks and min/max dimensions. Track labels and edges provide canvas editing; fields provide exact values. Deleting a track can delete its content, whereas reducing track count relocates content. [Grid flow](https://help.figma.com/hc/en-us/articles/31289469907863-Use-the-grid-auto-layout-flow) | The general auto-layout guide still labels grid open beta. Grid layout guides are a separate visual aid. |
| Padding and gap | Select an auto-layout frame; hover reveals padding handles. Drag for adjustment or click a handle for numeric entry. The panel starts with paired axes, permits individual sides and shorthand. Gap supports numeric values, nudging, scrubbing, or Auto distribution. [Horizontal/vertical flows](https://help.figma.com/hc/en-us/articles/31289464393751-Use-the-horizontal-and-vertical-flows-in-auto-layout) | Between, Evenly and Around have rollout differences. Spacing actions may change bindings, not just pixels. |
| Exact versus gestural editing | Numeric fields support typing, equations and label scrubbing. Shift changes nudge size. The earlier workflow report records opposite/all-side padding modifiers and distinct Scale versus resize behavior. [Numeric controls](https://help.figma.com/hc/en-us/articles/360039956914-Adjust-alignment-rotation-position-and-dimensions), [earlier task matrix](../figma-editing-workflows.md) | An 8-point nudge preference is not evidence of a variable-aware snapping system. Figma's lesson sets big nudge to 8 per person. [Design-system lesson](https://help.figma.com/hc/en-us/articles/14548865734679-Lesson-3-Build-your-design-system) |
| Text and wrapping | Text can use auto width, auto height or fixed sizing; resizing bounds and scaling text are different operations. Inline editing is separate from layer renaming. [Text sizing](https://help.figma.com/hc/en-us/articles/27378154668951-Adjust-text-dimensions-and-resizing), [text guide](https://help.figma.com/hc/en-us/articles/360039956434-Guide-to-text-in-Figma-Design) | Record both wrapping and parent reflow after a label change. Do not treat an editable text layer as a runtime form input. |
| Paints and image backgrounds | An image is a fill or stroke on a layer. The paint swatch opens Fill, Fit, Crop or Tile controls; crop and image adjustments are non-destructive. Scaling the layer changes the image presentation according to fill mode. [Image properties](https://help.figma.com/hc/en-us/articles/360041098433-Adjust-the-properties-of-an-image) | This supports image fills on ordinary design containers, not only standalone photo layers. Mapping them to `background-image` versus `<img>` is a code-generation decision. |
| Mixed selections | Selection colors groups variable, style and raw fills separately; it offers replacement, detachment and targeting layers using a color. It excludes images/video, hidden fills and masks. [Mixed colors](https://help.figma.com/hc/en-us/articles/360042553434-View-and-adjust-colors-in-a-mixed-selection) | A mixed selection is not a single generic value. Color provenance remains meaningful even when values look alike. |
| Controls and accessibility | F6 moves between major UI regions; Tab navigates within sections; Actions searches commands. Accessibility preferences include screen-reader adaptation and enhanced contrast. Some operations still require a pointer. [Keyboard controls](https://help.figma.com/hc/en-us/articles/360040328653-Use-Figma-products-with-a-keyboard) | Documentation is not a VoiceOver audit of this installed app. Prototype accessibility is separately enabled and has desktop/mobile limits. [Accessible prototypes](https://help.figma.com/hc/en-us/articles/7810391964695-Accessible-prototypes-in-Figma) |

**Unverified:** exhaustive property visibility for every selection, a general property-panel search, native child margin semantics in Design, every constraint/resizing combination, and keyboard accessibility of every handle. These require targeted observation rather than assumptions from web CSS.

## 3. Reuse and design systems

### Variables, styles and bindings

**Documented:** styles combine values, such as a typography set or layered fills. Variables hold typed values with one active mode value at a time; variables can alias variables and back style properties. A style is not itself an aliasable variable. [Variables versus styles](https://help.figma.com/hc/en-us/articles/15871097384471-The-difference-between-variables-and-styles)

| Relationship | Documented behavior | Consequence |
| --- | --- | --- |
| Variable definition and alias | Variables live in collections/groups; aliases reference variables of the same type, including discoverable library values. An alias can be detached. [Manage variables](https://help.figma.com/hc/en-us/articles/15145852043927-Create-and-manage-variables-and-collections) | Editing a definition, changing its alias, and replacing a consumer's binding are different operations. |
| Scope | Number, color and string scopes filter which property pickers offer a variable. For example, a radius-only number does not appear as padding. [Manage variables](https://help.figma.com/hc/en-us/articles/15145852043927-Create-and-manage-variables-and-collections) | Scope is discoverability/application policy, not a synonym for theme or mode. |
| Bind and detach | Property controls apply local or published variables. Color variables/styles share a picker with different swatch shapes. Numeric properties have variable controls; canvas padding/gap editing explicitly detaches number variables. [Apply variables](https://help.figma.com/hc/en-us/articles/15343107263511-Apply-variables-to-designs) | Matching a number does not preserve the binding. Dragging a token-bound 16 to 24 is not automatically choosing a named 24 token. |
| Mode and inheritance | Modes give context-dependent values. Objects/pages can use an explicit mode or inherit Auto/Default; changing a collection's default does not retarget an explicitly chosen mode. [Modes](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables) | A visible value depends on binding plus mode, not just the definition's first value. |
| Import/export existing tokens | Modes export to JSON; DTCG JSON import creates modes, with supported-type constraints: dimensions require px and font families a single string; normalized-name collisions drop later duplicates. Cross-collection aliases use Figma extension metadata. [Modes, import sections](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables) | Token portability is documented, but not a lossless import of arbitrary CSS/Tailwind or every DTCG token type. |
| Propagate cross-file changes | Library updates are reviewed and accepted. Nested dependencies can require upstream files to accept and republish before a downstream mode conflict resolves. [Modes, conflicts](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables) | A consumer seeing a stale mode is not necessarily broken inheritance; publication state matters. |

**Unverified continuation:** extend the successful direct-binding test below with a primitive → alias → card binding; change the primitive, then drag the card's padding handle. Inspect identity as well as pixels.

**Source correction:** the older comparison article still says scopes beyond numbers and code syntax are forthcoming. The dedicated management article documents color/string scopes and working platform code syntax. Use the specific feature page for those current capabilities; do not repeat the stale sentence. [Older comparison](https://help.figma.com/hc/en-us/articles/15871097384471-The-difference-between-variables-and-styles), [current management](https://help.figma.com/hc/en-us/articles/15145852043927-Create-and-manage-variables-and-collections)

### Components, instances, overrides and libraries

**Documented:** the main component defines reusable content; an instance stays linked while allowing supported overrides. Local reuse is available without publishing a team library. [Component guide](https://help.figma.com/hc/en-us/articles/360038662654-Guide-to-components-in-Figma)

| Task | Documented route and outcome |
| --- | --- |
| Offer intentional controls | A main component exposes text, boolean visibility, instance swap, variant and slot properties. Preferred swaps constrain the suggested choices. Nested component properties can be surfaced on the top-level instance. Slots permit content changes without detaching. [Component properties](https://help.figma.com/hc/en-us/articles/5579474826519-Explore-component-properties) |
| Choose a state or size | A component set contains variants with named property/value combinations. Dragging the asset inserts the default variant; the instance's dropdowns choose another combination. Importing an instance brings the set's variants with it. [Variants](https://help.figma.com/hc/en-us/articles/360056440594-Create-and-use-variants) |
| Change this use | Change an exposed property or a permitted nested property. Reset a specific override or all changes from the instance menu; reset restores the main definition rather than merely undoing the most recent chronological action. [Instance changes](https://help.figma.com/hc/en-us/articles/360039150733-Apply-changes-to-instances) |
| Change the shared definition | Go to main component, edit in its source file, and use Return to instance after cross-file travel. Same-file instances update immediately; cross-file consumers require library publication. [Edit main components](https://help.figma.com/hc/en-us/articles/360038665934-Edit-main-components) |
| Discover and migrate assets | Assets and instance menus expose component descriptions and documentation links. Swap libraries matches styles, components and variables; unmatched assets remain attached to the original. [Descriptions](https://help.figma.com/hc/en-us/articles/7938814091287-Add-descriptions-to-styles-components-and-variables), [swap libraries](https://help.figma.com/hc/en-us/articles/4404856784663-Swap-libraries) |
| Review propagation | Library updates offer side-by-side or overlay comparison and navigation among affected instances before update. Updates can be accepted individually or together; hidden-layer changes cannot be visually compared. [Review updates](https://help.figma.com/hc/en-us/articles/360039234193-Review-and-accept-library-updates) |
| Leave the relationship | Detach converts an instance to a regular frame, preserves its present layers/properties, and stops main-component updates. [Detach](https://help.figma.com/hc/en-us/articles/360038665754-Detach-an-instance-from-the-component) |

**Inferred:** the useful precedent is a visible distinction between “change this use,” “change its definition,” “reset my exception,” and “stop inheriting.” It does not establish that React function calls should adopt Figma's complete override model. **Unverified:** a complete cross-project usage browser for every variable/component was not established; local same-instance selection and update review are narrower capabilities.

**Freshness:** simplified instances were scheduled for deprecation starting March 23, 2026, with all properties/layers visible again. A report claiming hidden nested structure is central to current Figma component editing would need account-specific evidence. [Component properties](https://help.figma.com/hc/en-us/articles/5579474826519-Explore-component-properties)

### Executable reuse in Make

**Documented:** Make kits can use public or private React npm design-system packages, so reuse can involve actual interactive component code. Private packages have paid-plan and registry administration requirements. [Design-system packages](https://help.figma.com/hc/en-us/articles/35946832653975-Use-your-design-system-package-in-Make-kits)

**Documented:** kits combine packages, imported Design library styles and guidelines. The style extraction is explicitly incomplete: only a subset of variables becomes a global CSS file of raw values; original token syntax is not preserved exactly. Kit CSS/guideline edits do not update the original Design library. Updating the imported library requires re-adding it and preserving/reapplying custom guidelines. [Make kits, FAQs](https://help.figma.com/hc/en-us/articles/39241689698839-Get-started-with-Make-kits)

**Inferred:** “uses the same design system” has two materially different meanings here: executing the same React package versus extracting approximate style context from a design library. A comparison must state which path was tested.

## 5. Code, source ownership and agents

| Workflow | Documented mechanism | Ownership interpretation |

| Design → code context | MCP reads design context, metadata, screenshots and variable definitions. [MCP tools](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/), [Code Connect](https://developers.figma.com/docs/code-connect/) | **Inferred:** mapping a component and its props improves implementation context; it is not proof that Design edits directly mutate the repository. |

Full seat plus file edit access is required. [Write to canvas](https://developers.figma.com/docs/figma-mcp-server/write-to-canvas/) | The agent writes real editable design structure. | Running browser UI → Design → agent implementation | `generate_figma_design` captures a screen or flow into native editable layers. [Code to canvas](https://developers.figma.com/docs/figma-mcp-server/code-to-canvas/) | **Inferred:** this is a capture/review/implementation round trip, not evidence of persistent node-to-AST binding or automatic preservation of arbitrary source structure. |

[Copy Make preview](https://help.figma.com/hc/en-us/articles/35060759685015-Copy-a-Figma-Make-preview-as-design-layers) | Snapshot conversion. [Push to GitHub, FAQs](https://help.figma.com/hc/en-us/articles/35463818346647-Push-from-Figma-Make-to-GitHub) | Explicitly one-way. “GitHub integration” alone is not a bidirectional ownership guarantee. |

[Local-code beta announcement](https://www.figma.com/blog/figma-make-now-on-your-local-code/) | **Documented counterexample to a blanket no-existing-repo claim.** Local code is edited. This is stronger than ordinary Copy design. The launch account describes the beta workflow; the ordinary Make help page still explicitly describes disconnected snapshots. The precise detection, identity preservation and available release were not tested. [Local-code beta announcement](https://www.figma.com/blog/figma-make-now-on-your-local-code/)

## Assumptions changed and implications for Spool

These are **inferences for comparison**, not implementation recommendations:

1. Figma spans native design simulation and executable application work. A comparison based only on Design's prototype noodles misses Make, playable embeds, Sites code layers and the local-codebase beta.
2. “Round trip” needs a mechanism. Code Connect references, code-to-canvas capture, disconnected Make copies, one-way GitHub export and local-repository editing have different source ownership and failure modes.
3. Token inventory is only the start. Alias identity, mode context, property scope, binding detachment and publication state explain what an edit actually changes. Numeric equality is weaker evidence than preserved provenance.
4. Shared reuse has both content and code paths. A native component instance, a raw-CSS style extraction and an executable npm package cannot be treated as equivalent design-system integration.
5. Figma makes some relationship changes explicit: instance reset, main-component travel and return, detachment, and review of library updates. These are relevant workflow precedents; copying its complete data model is a separate decision.
6. A clean visual panel can still queue an agent-mediated source change. Its immediacy, determinism and cost must be measured in the actual surface, particularly given Make's old/new editing split.
