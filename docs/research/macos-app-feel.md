# Mac app feel

2026-09-05. Initial investigation, not an implementation decision or a redesign spec.

Spool can make substantial progress toward a Mac experience within Electron. The first boundary to improve is between the canvas and the operating system: commands, opening projects, window behavior, and presentation around the canvas. Moving the existing page into a Swift window would leave that page's controls unchanged.

This is a source review. The checkout app was launched, but direct Mac inspection failed because the computer-use service was not configured. Browser inspection also failed during connection setup. No visual, keyboard-routing, rendering-quality, or performance claims below are based on a successful live inspection.

| Area to assess | Evidence and implication |
| --- | --- |
| Menus and commands | [The app menu](../../desktop/src/main.ts#L497) offers Open Canvas on Cmd+N, with generic Edit and View commands. Settings exists on [Cmd+, inside the page](../../src/ui/hotkeys.ts#L444), but has no application-menu entry. The desktop [canvas bridge](../../desktop/src/canvas-preload.ts) only exposes updates. Apple's [menu tutorial](https://developer.apple.com/tutorials/app-dev-training/customizing-menus-with-commands-and-shortcuts) treats menus and shortcuts as alternate routes to an app's actual actions. Connecting them to Spool would improve discoverability and consistency. |
| Canvas zoom | The app's View menu uses Electron's zoom roles. [Electron's implementation](https://github.com/electron/electron/blob/main/lib/browser/api/menu-item-roles.ts) changes the web contents' zoom level, while [Spool's shortcuts](../../src/ui/hotkeys.ts#L262) describe camera zoom. These are different operations. Routing menu commands to the canvas is a concrete integration opportunity; shortcut interception and behavior with focus inside frames still need live checking. |
| Opening projects | The current [folder picker](../../src/ui/picker.tsx) is a custom web interface. Electron already provides a [native directory chooser](https://www.electronjs.org/docs/latest/api/dialog) and [Open Recent integration](https://www.electronjs.org/docs/latest/tutorial/recent-documents). A native opening path could use the same project-opening rules underneath. Choosing its relationship to Spool's existing search is a product decision. |
| Window presentation | The [main window](../../desktop/src/main.ts#L141) uses the standard title bar above the [page's own header](../../src/ui/app.tsx#L391). The [player](../../desktop/src/main.ts#L395) already integrates system traffic lights into its header. Electron supports [inset traffic lights and native vibrancy materials](https://www.electronjs.org/docs/latest/api/base-window). Those capabilities permit a more integrated main window, but do not turn HTML controls into AppKit controls. Exact layout, typography, and material use need visible variants and Liam's choice. |
| Window persistence and settings | Player bounds are saved in [the app](../../desktop/src/main.ts#L382); the main window starts from fixed dimensions with no corresponding persistence. [Settings](../../src/ui/settings-sheet.tsx#L64) is an overlay within the page. Remembering the main window and considering a separate Settings window are possible Electron changes. The latter is a presentation choice, not a prerequisite for useful settings. |

There is already Mac integration to preserve: Close and Quit have different lifecycles, Dock activation restores the canvas, menus and the status item are native, and the app has a signed update path. See [the lifecycle and menus](../../desktop/src/main.ts) and [update handling](../../desktop/src/updates.ts). The UI also supports system appearance and reduced motion in [its styles](../../src/ui/ui.css); their absence is not the problem.

Swift changes which parts are native only when those parts are implemented with native views. Apple's [Mac app tutorial](https://developer.apple.com/tutorials/swiftui/creating-a-macos-app) demonstrates native toolbars, commands, and settings. A Swift shell could own those surfaces while a [WKWebView](https://developer.apple.com/documentation/webkit/wkwebview) renders Spool's web content. Replacing the canvas itself would be a much larger change because live TSX frames are web documents, as established in [the rendering ADR](../adr/0003-canvas-iframes-player-single-document.md).

There is a specific rendering question before considering WKWebView. The [desktop rationale](../../desktop/README.md) records blurry transformed iframes under WebKit. WebKit [bug 133801](https://bugs.webkit.org/show_bug.cgi?id=133801), still marked NEW when checked, describes blurry scaled content when an iframe includes fixed-position content. This supports treating the issue as a migration risk. It does not prove how current macOS renders today's Spool canvas; that requires a fresh comparison using representative frames and zoom levels.

My recommendation for discussion is to keep Electron for the first Mac-focused pass: connect the native menus to existing commands, assess native project opening and window restoration, and explore the main window's presentation. Reconsider Swift if native controls throughout the surrounding interface become a settled requirement and a current WebKit comparison passes. A language change by itself would not resolve the identified command and workflow gaps.
