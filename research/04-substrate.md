## 1. tldraw SDK (tldraw.dev)

**License terms**
- Free only for local development (non-production). Production requires one of three license types: **Trial** (100 days, free, one per commercial entity, no grace period at expiry), **Commercial** (paid, contact sales), or **Hobby** (free, non-commercial projects only, discretionary approval). [tldraw license docs](https://tldraw.dev/community/license) / [license key docs](https://tldraw.dev/sdk-features/license-key)
- **Watermark rule, verbatim from the live page today**: *"When using the tldraw SDK under a hobby license, the 'made with tldraw' watermark must be shown on the canvas."* Trial and Commercial licenses carry no watermark. [tldraw license docs](https://tldraw.dev/community/license)
- **Pricing — important nuance**: I fetched the raw HTML of `tldraw.dev/pricing` directly (not just the rendered summary) and it currently contains **zero dollar figures**. Every tier CTA reads "Value-based pricing," "Apply for startup pricing," "Apply for a hobby license," "Talk to sales." [tldraw.dev/pricing](https://tldraw.dev/pricing)
- The commonly-cited **$6,000 USD/year** Startup license figure (with community discussion of a ~10-seat cap) comes from press coverage and Hacker News discussion of the September 2025 SDK 4.0 relicensing — it is **not** stated anywhere on tldraw's current official pricing page, so treat it as historical/secondhand rather than confirmed-current. [BigGo News coverage](https://biggo.com/news/202509190115_tldraw_SDK_4.0_Licensing_Debate) / [HN discussion](https://news.ycombinator.com/item?id=45294916)
- Rationale for the license change (from the founder): moving off permissive licensing to "capture some of the value that tldraw brings to the companies that use it in commercial products." [License updates post](https://tldraw.substack.com/p/license-updates-for-the-tldraw-sdk)
- Annual/perpetual licenses get a 30-day grace period after expiry; trial licenses do not. License keys are validated client-side and safe to expose publicly. [license key docs](https://tldraw.dev/sdk-features/license-key)
- Current npm package version: `5.2.5`, license field literally reads `"SEE LICENSE IN LICENSE.md"` (verified via npm registry metadata directly).

**Can custom shapes host iframes/arbitrary HTML+DOM?** Yes, at two levels:
- Built-in **Embed shape**: renders iframe content from 24+ recognized providers (YouTube, Figma, CodeSandbox, Google Maps/Calendar/Slides, Vimeo, Spotify, etc.), each with provider-specific default dimensions and sandbox overrides. Users can also paste raw `<iframe>` HTML for *any* http(s) source to create an embed even without a known provider. Default sandbox permissions: `allow-scripts`, `allow-same-origin`, `allow-forms`, `allow-popups` allowed; `allow-downloads`, `allow-modals`, `allow-pointer-lock`, `allow-top-navigation` blocked (overridable per embed definition). Custom embed types are defined via `EmbedShapeUtil.configure()`. GitHub Gist embeds specifically use `srcDoc`. [Embed shape docs](https://tldraw.dev/sdk-features/embed-shape) / [Custom embeds](https://tldraw.dev/examples/custom-embed)
- Fully **custom shapes**: built via a `ShapeUtil` subclass with a `component()` method returning arbitrary JSX wrapped in tldraw's `HTMLContainer` — *"There's a lot of flexibility here, and you can use any React hooks you want and return any valid JSX,"* meaning iframes/arbitrary DOM are fair game. [Custom shape docs](https://tldraw.dev/examples/custom-shape)
- **Direct precedent**: tldraw's own flagship example, **Make Real**, is exactly this pattern — a custom `PreviewShape` renders AI-generated HTML inside an iframe on the canvas. Per the tldraw team: *"Because tldraw's canvas has always been made of regular HTML, its canvas can support iframes directly."* [Make Real: the story so far](https://tldraw.dev/blog/make-real-the-story-so-far) / [make-real-starter repo](https://github.com/tldraw/make-real-starter)

**Canvas features out of the box**
- **Snapping**: bounds snapping (edges/centers/corners), handle snapping (e.g. arrow tips to shape points), gap snapping (equal spacing), with live snap-line feedback. [Snapping docs](https://tldraw.dev/sdk-features/snapping)
- **Frames**: shapes snap to frame interiors; frames act as snap/containment targets. [Default shapes docs](https://tldraw.dev/sdk-features/default-shapes)
- **Arrows**: bind to shapes and auto-update on move, support arc or elbow (right-angle) routing, text labels, multiple arrowhead styles.
- **Keybinds**: number-key tool selection, zoom/pan shortcuts, standard editing shortcuts — extensively documented across release notes. [Release notes](https://tldraw.dev/blog/release-notes)
- **Minimap**: yes (a "Lightspeed minimap" per recent release notes).
- All of the above ship by default and are individually replaceable/hideable via the UI component system below.

**Documented performance limits**
- Default cap of **4,000 shapes per page** (raised from 2,000; configurable via `maxShapesPerPage`). [Performance docs](https://tldraw.dev/sdk-features/performance) / [GH issue on the old 2,000 limit](https://github.com/tldraw/tldraw/issues/4028)
- Debounced zoom auto-enables above **500 shapes** (`debouncedZoomThreshold`).
- Viewport culling is the core mechanism: off-screen shapes get `display: none`; example given: *"a canvas with 10,000 shapes might only render 50 if the rest are out of view."* Backed by an R-tree spatial index for fast hit-testing/selection at scale. [Culling docs](https://tldraw.dev/sdk-features/culling) / [DeepWiki: shape rendering & culling](https://deepwiki.com/tldraw/tldraw/3.4-shape-rendering-and-culling)
- Known rough edge: drawing a shape exactly at the max-shapes-per-page limit can crash the editor (open GitHub issue). [Issue #5781](https://github.com/tldraw/tldraw/issues/5781)
- Monitoring APIs: `editor.getCurrentPageShapeIds().size`, `editor.getCulledShapes().size`, `editor.getEfficientZoomLevel()`.

**Can the editor chrome be fully replaced?** Yes.
- The `hideUi` prop strips the default toolbar, style panel, and pages menu entirely, letting you build a fully custom UI around the bare `Editor`. [Custom UI example](https://tldraw.dev/examples/custom-ui) / [Hide UI example](https://tldraw.dev/examples/hide-ui)
- The UI is composed of 25+ named, individually-replaceable component slots (toolbars, menus, panels, dialogs) passed as props. [UI components docs](https://tldraw.dev/sdk-features/ui-components)
- `useEditor()` and `useActions()` hooks expose full programmatic access to editor state and actions for building custom chrome. [User interface docs](https://tldraw.dev/docs/user-interface)
- Two canvas-layering primitives matter for a Figma-like host app: content that should pan **and** zoom with the camera lives in the canvas HTML layer (scales like a shape); content that should only pan (not zoom), like a toolbar, lives in the overlay layer. [Things on the canvas](https://tldraw.dev/examples/things-on-the-canvas)

## 2. Alternatives

**Excalidraw** — MIT licensed, 127,913 GitHub stars (verified live via GitHub API). Rendering architecture is a **two-canvas raster** setup: a static `<canvas>` draws shape primitives via RoughJS, and a separate interactive `<canvas>` handles selection/cursor overlays, coordinated by a `Renderer`/`Scene` pair that does viewport-based culling of what's visible. [DeepWiki: rendering architecture](https://deepwiki.com/excalidraw/excalidraw/6.1-rendering-architecture) / [DeepWiki: rendering & export](https://deepwiki.com/excalidraw/excalidraw/5-rendering-and-export). Critically, **embeddable elements are real DOM `<iframe>`s, not raster** — the `renderEmbeddable` prop *"allows you to replace the renderer for embeddable elements (which renders `<iframe>` elements),"* paired with a `validateEmbeddable` prop to control which URLs are allowed. So Excalidraw is architecturally the same hybrid as tldraw: raster canvas for drawing primitives, real overlaid DOM iframes for live content. Ships as an embeddable React component. [Render props docs](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/render-props) / [Integration guide](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/integration)

**xyflow / React Flow** — MIT licensed, 37,713 stars (verified via GitHub API). Purpose-built for node-graphs/diagrams, not freeform whiteboarding. Custom nodes are literally just React components — *"all you need to do is create a React component"* — rendered as plain DOM (`div`, `input`, etc.), with React Flow wrapping them in a container that injects id/position/data and drag/selection/connection handlers. [Custom nodes docs](https://reactflow.dev/learn/customization/custom-nodes). There is no raster layer at all; "HTML nodes are native" because the whole graph *is* DOM+CSS. Performance guidance is accordingly React-shaped rather than canvas-shaped: memoize custom node/edge components, `useCallback` event handlers, avoid subscribing to the full `nodes` array, use `hidden` to collapse subtrees instead of unmounting, `onlyRenderVisibleElements` for viewport virtualization, `snapToGrid` to throttle state updates, and simplify CSS (shadows/animations) as a last resort. No official max-node benchmark is published; community issues report jank around 10k+ unoptimized nodes. [Performance docs](https://reactflow.dev/learn/advanced-use/performance) / [GH discussion #4975](https://github.com/xyflow/xyflow/discussions/4975) / [Issue #3044 — 10k nodes laggy](https://github.com/xyflow/xyflow/issues/3044)

**Konva / Pixi.js** — Konva is MIT licensed (confirmed via npm registry; GitHub's license-detector mis-flagged it as "NOASSERTION"). Both are **canvas-raster**: Konva uses the 2D Canvas API with an object-oriented scene graph — each `Layer` actually draws to *two* `<canvas>` elements, one visible scene canvas and one hidden hit-test canvas for event detection. [Konva overview](https://konvajs.org/docs/overview.html). Pixi.js is WebGL/WebGPU-accelerated, aimed at games/many moving sprites/high frame rate rather than UI editing interactions. Neither can put a live iframe *inside* the raster bitmap — DOM content must be a separately-positioned overlay kept in sync with the canvas's pan/zoom transform. Konva documents this pattern first-party: the companion `react-konva-utils` package's `Html`/portal component lets you render real DOM nodes (inputs, divs) "as part of your canvas tree." [Konva DOM portal docs](https://konvajs.org/docs/react/DOM_Portal.html). No equivalent first-party DOM-overlay helper was found documented for Pixi.js in this research — you'd hand-roll the same absolute-position-plus-shared-transform technique.

**Purpose-built "infinite canvas with DOM children" libraries actually in use, 2025-2026** — this category is thin. tldraw is the dominant production choice (see §1). Beyond it: **Kinopio** is a real, open-sourced production app (cards + connections on an infinite canvas, ~220kb client) whose client was open-sourced in 2024; its own docs note it does direct DOM manipulation for some canvas-covering layers. [kinopio-client repo](https://github.com/kinopio-club/kinopio-client) / [Open-sourcing announcement](https://pketh.org/open-sourcing-kinopio.html). **Tela** (by Deta, for Svelte) is explicitly *"a declarative infinite canvas library... using native DOM elements"* so *"you can use any existing HTML, CSS, JS component inside a canvas,"* with pan/zoom, viewport culling, and grid-snap built in. [deta/tela repo](https://github.com/deta/tela). Smaller/newer entrants surfaced in search but not verified as production-proven: `Flowscape-UI/canvas-react` and `awaisshah228/infinit-canvas` (the latter claims OffscreenCanvas+Web Worker rendering handling 5,000+ cards at 60fps with React-DOM virtualization limited to on-screen nodes). [canvas-react repo](https://github.com/Flowscape-UI/canvas-react) / [infinit-canvas repo](https://github.com/awaisshah228/infinit-canvas). **UNCONFIRMED**: several 2026 "best infinite canvas" blog posts (Bookmarkify, Storyflow, OmniCanvas) claim live-iframe-card products, but these read as SEO/marketing content rather than engineering documentation — I'm not treating them as verified technical sources.

## 3. Browser facts: many live iframes on one page

**Practical iframe-count limits (Chromium)**
- Site Isolation puts each **cross-site** iframe (different eTLD+1) in its own renderer process by default; **same-site** iframes share the parent's process. [Chromium site isolation docs](https://www.chromium.org/Home/chromium-security/site-isolation/) / [process model docs](https://chromium.googlesource.com/chromium/src/+/main/docs/process_model_and_site_isolation.md)
- Concrete real-world number: *"a single news article with three ad networks can generate 8–12 subframe processes."* [webperf.tips](https://webperf.tips/tip/iframe-multi-process/)
- Memory overhead of Site Isolation itself was measured by the Chrome team at roughly **10–13% on desktop** with many tabs open — on a 4GB machine with 10 tabs, ~50–130MB extra. [Chromium site isolation docs](https://www.chromium.org/Home/chromium-security/site-isolation/) / [SSL Store writeup](https://www.thesslstore.com/blog/google-chrome-site-isolation/)
- Out-of-process iframes use lightweight `RemoteFrame` placeholders in non-hosting processes, which cost far less memory than a full `LocalFrame` — so cost isn't strictly linear per cross-site iframe. [OOPIF docs](https://www.chromium.org/developers/design-documents/oop-iframes/)
- No official hard cap on iframe count is published anywhere I found. Practical implication for this use case: if every hosted "screen" is a same-origin `srcdoc` sandboxed iframe, they should mostly share one renderer process rather than each spawning a new OS process — worth validating empirically rather than assuming per-iframe process cost (this specific inference is mine, not a quoted source). Same-site/same-process iframes do compete for one thread and can be OOM-killed together. [webperf.tips](https://webperf.tips/tip/iframe-multi-process/)

**`srcdoc` + `sandbox`**
- Full current sandbox token list (verified live against MDN): `allow-downloads`, `allow-forms`, `allow-modals`, `allow-orientation-lock`, `allow-pointer-lock`, `allow-popups`, `allow-popups-to-escape-sandbox`, `allow-presentation`, `allow-same-origin`, `allow-scripts`, `allow-storage-access-by-user-activation`, `allow-top-navigation`, `allow-top-navigation-by-user-activation`, `allow-top-navigation-to-custom-protocols`. [MDN iframe reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)
- **`allow-scripts` without `allow-same-origin`**: scripts run, but the document is forced into a unique **opaque/null origin** that always fails same-origin checks — no access to the parent's storage, cookies, or DOM. This is the documented-safe combination for untrusted content, and `postMessage()` works normally regardless of the null origin — it's the intended communication channel. [MDN iframe reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe) / [Mozilla Discourse thread](https://discourse.mozilla.org/t/whats-the-point-of-forbidding-a-sandboxed-iframe-with-allow-scripts-and-allow-same-origin/81365)
- **`allow-scripts` + `allow-same-origin` together** are explicitly discouraged when the framed doc is actually same-origin with the embedder, because the framed doc can then call script to strip its own `sandbox` attribute, "making it no more secure than not using the sandbox attribute at all." [MDN iframe reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)
- `srcdoc` documents get origin `about:srcdoc` and inherit the **embedding document's URL** as the base URL for relative links; an explicit `<base href="about:srcdoc">` is needed if in-page anchors should resolve against the fragment itself. `srcdoc` + `sandbox` compose cleanly and are the documented pattern for safely displaying untrusted/user-generated HTML. [MDN iframe reference](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)
- tldraw itself uses `srcDoc` specifically for GitHub Gist embeds, with hex-only validation to prevent injection. [tldraw embed shape docs](https://tldraw.dev/sdk-features/embed-shape)

**CSS transform `scale` on iframes — known bugs**
- Confirmed, long-standing **WebKit-specific** bug (filed 2014, status still "NEW"/unresolved at last recorded update): any CSS transform on an ancestor (not just `scale` — `rotateY` too) causes iframe content to render blurred. A maintainer comment: *"Iframe content is always blurred when inside an element that has any CSS transform on it"* in WebKit, and explicitly *"Firefox is fine"* — i.e., not cross-browser. Standard raster workarounds (`translate3d(0,0,0)`, `backface-visibility: hidden`) do **not** fix it per the same thread. [WebKit Bug 133801](https://bugs.webkit.org/show_bug.cgi?id=133801)

**Pointer events over scaled iframes**
- Per the Pointer Events spec, once CSS transforms are applied, "an element's coordinate space may differ from screen coordinate" (e.g., a 90°-rotated element's local X axis maps to the screen's Y axis) — browsers are expected to hit-test/dispatch through the active transform. [MDN Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events) / [W3C Pointer Events spec](https://www.w3.org/TR/pointerevents3/)
- Applied confirmation: tldraw's embed shape docs state plainly that *"in editing mode, pointer events pass through to the iframe. You can scroll, click buttons, and interact with the embedded content"* while the shape itself sits on a pannable/zoomable canvas. [tldraw embed shape docs](https://tldraw.dev/sdk-features/embed-shape)
- A specific, documented adjacent bug: toggling `pointer-events: none` on an iframe causes scrolling to intermittently break in Chrome 63+ on macOS. [interact.js Issue #605](https://github.com/taye/interact.js/issues/605)

**Capturing screenshots/thumbnails of iframe content**
- **html2canvas / DOM-serialization tools** cannot capture cross-origin iframe content at all (blocked by Same-Origin Policy); even same-origin iframe content is described as "notoriously difficult... often won't show up correctly, if at all." The only documented workaround without a capture API is cooperative: `postMessage` the iframe asking it to self-capture and message back a data URL, or fetch+render server-side as a proxy. [html2canvas Issue #487](https://github.com/niklasvh/html2canvas/issues/487)
- **SVG `foreignObject` rasterization** (the technique underlying html2canvas-style libraries): serialize a DOM subtree to an XHTML string inside `<foreignObject>` inside `<svg>`, serialize that to a data URL, load into an `Image`, draw to `<canvas>`. Documented limits: cross-origin images without CORS headers won't load; stylesheet-declared (non-inline) styles don't pass through; external resources (fonts/images) not yet loaded won't appear because the browser doesn't wait for them. [MDN foreignObject](https://developer.mozilla.org/en-US/docs/Web/SVG/Reference/Element/foreignObject) / [semisignal.com writeup](https://semisignal.com/rendering-web-content-to-image-with-svg-foreign-object/)
- **Direct production confirmation of the same wall**: tldraw's Make Real team hit exactly this — exporting the canvas as an image renders embedded iframes as "empty rectangles" because *"iframes are essentially a black box to the website that contains it."* [Make Real: the story so far](https://tldraw.dev/blog/make-real-the-story-so-far)
- **Element Capture API**: captures a specific DOM element + only its own descendants as a `MediaStream` video track (excludes overlapping content from other elements). Shipped (non-origin-trial) in Chrome desktop from **Chrome 132**; explicitly *"only enabled for self-capture"* (i.e., capturing your own tab via `getDisplayMedia`, not an arbitrary page); desktop-only, no mobile; I found no Safari or Firefox support in any source checked. [Chrome for Developers: Element Capture](https://developer.chrome.com/docs/web-platform/element-capture) / [MDN Element/Region Capture](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Capture_API/Element_Region_Capture)
- **Region Capture API**: crops a `getDisplayMedia()` stream to an element's *bounding box* (not its exact shape), so overlapping content can leak into frame — a materially weaker guarantee than Element Capture. Same desktop-only ecosystem. [Chrome for Developers: Region Capture](https://developer.chrome.com/docs/web-platform/region-capture)
- Both capture APIs require the tab to already be under active `getDisplayMedia()` capture — **not** an on-demand "screenshot any element right now" primitive, which limits their fit for thumbnailing many canvas cards simultaneously (this scoping inference is mine based on the API shape, not a direct quote).
- **Server-side Playwright capture** sidesteps all of the above because Playwright drives a real browser engine over the Chrome DevTools Protocol rather than doing same-origin DOM access from in-page JS. It exposes `frameLocator()`/`Frame` objects to target elements inside any iframe, plus standard element (`locator.screenshot()`) and full-page (`page.screenshot({ fullPage: true })`) capture. [Playwright: Frames](https://playwright.dev/docs/frames) / [Playwright: Screenshots](https://playwright.dev/docs/screenshots). Note: I could not find a single Playwright doc page explicitly stating "this works across cross-origin iframe boundaries" in so many words — that's standard, widely-relied-upon CDP behavior (compositor-level screenshot, origin-agnostic) rather than a directly quoted claim, so I'm flagging the mechanism explanation as my own technical framing on top of the confirmed frame-targeting/screenshot APIs.

## 4. View Transitions API (mid-2026 status)

**Same-document** (`document.startViewTransition()`): **Chrome 111+, Edge 111+, Safari 18.0+, Firefox 144+** (global support 88.46% per caniuse, checked live today). [caniuse: View Transitions API (single-document)](https://caniuse.com/view-transitions)

**Cross-document** (the `@view-transition` at-rule + browser-driven MPA transitions): **Chrome 126+, Edge 126+, Safari 18.2+ fully supported; Firefox not supported in any released version** per caniuse's live matrix checked today. [caniuse: @view-transition at-rule](https://caniuse.com/mdn-css_at-rules_view-transition)
- Opt-in requires **both** the departing and arriving document to declare `@view-transition { navigation: auto; }`; only triggers on user-initiated, same-origin navigations (not programmatic redirects, cross-origin links, or POST submissions). [Chrome: cross-document view transitions](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document) / [CSS-Tricks gotchas writeup](https://css-tricks.com/cross-document-view-transitions-part-1/)
- Chrome 126 explicitly scoped this to **main-frame navigations only**; iframe navigations were called out as "following in a later Chrome release" and, as of this research, remain gated behind `chrome://flags/#view-transition-on-navigation-iframe` rather than shipped by default. [Chrome 126 blog post](https://developer.chrome.com/blog/new-in-chrome-126)
- New lifecycle events: `pageswap` (fires on the outgoing document, lets you set `view-transition-name` before the snapshot) and `pagereveal` (fires on the incoming document). [MDN View Transition API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API)
- Hard **4-second timeout**: if the new page doesn't reach a browser-defined "renderable" state within 4 seconds of navigation start (clock includes network/TTFB), the transition silently dies with no console warning. [CSS-Tricks gotchas writeup](https://css-tricks.com/cross-document-view-transitions-part-1/)

**`view-transition-name` matching model**: any element in the "old" state and any element in the "new" state that share the same `view-transition-name` are paired and treated as two visual states of one conceptual entity, *"even though the elements themselves are not necessarily referring to the same object."* `view-transition-name: match-element` auto-assigns a unique internal name per element so you don't hand-name everything, but it's explicitly **same-document only** since the auto-generated identifiers aren't stable across documents. [MDN view-transition-name](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/view-transition-name)

**What it can animate**: the browser builds a pseudo-element tree per named element — `::view-transition-group(name)` (wraps and receives the transform/size interpolation) containing `::view-transition-image-pair(name)`, which contains `::view-transition-old(name)` (a static bitmap snapshot of the old box, rendered like a replaced `<img>`) and `::view-transition-new(name)` (the live new box). Default behavior gives you a cross-fade of opacity plus smooth interpolation of the group's position/size/transform between old and new geometry — this is what makes shared-element morphs work without manual FLIP code. Because these are just pseudo-elements, any standard CSS animation (opacity, transform, clip-path, filter, `mix-blend-mode`, custom keyframes/easing/duration) can be applied, or you can bypass CSS defaults entirely and drive it via the Web Animations API off the `transition.ready` promise. [MDN: Using the View Transition API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API/Using)

**Known limits directly relevant to "smart animate" between HTML screens**:
- **Input/focus state is not preserved** — *"the API animates pixels, not focus."* Keyboard focus stays on the old element unless you explicitly call `element.focus()` inside the `startViewTransition` callback. [Chrome: view-transitions misconceptions](https://developer.chrome.com/blog/view-transitions-misconceptions)
- **Iframes are isolated from the transition system in both directions**: a view transition running inside an iframe does not propagate to the parent document, and a parent-document transition does not paint into a child iframe — you cannot make an iframe's content participate in a shared-element morph from outside it. [MDN View Transition API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API)
- For cross-document/MPA transitions specifically, an iframe **reloads its content whenever it's re-inserted** into the target page, so an iframe cannot be used to "persist" live state across a transition. Reported instability: *"iframes and cross-document transitions are a rough combination right now,"* including browser crashes reported on subsequent navigation inside an iframe; the suggested workaround is server-side detection to disable transitions when inside an iframe. [CSS-Tricks gotchas writeup](https://css-tricks.com/cross-document-view-transitions-part-1/)
- Default snapshot sizing applies `object-fit: fill`, visually stretching/distorting aspect ratio unless you override `object-fit` on the `::view-transition-old()/::view-transition-new()` pseudo-elements yourself. [CSS-Tricks gotchas writeup](https://css-tricks.com/cross-document-view-transitions-part-1/)
- Accessibility risk: because old and new content briefly coexist in the DOM, there's documented risk of lost reading position, focus confusion, and odd live-region announcement ordering. [MDN View Transition API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API)

**Synthesis for this use case** (researcher's own reasoning connecting the above, not an external claim): since each hosted "screen" in a canvas like this would live inside its own iframe, and VT explicitly does not let a parent-page transition reach into a child iframe's rendered content, native View Transitions could handle the canvas-level chrome (animating an iframe's *container* as it moves/resizes/morphs between canvas states) but cannot natively cross-fade or morph what's rendered *inside two different iframes* — that would have to happen inside each iframe's own document (its own same-document VT) or be faked with captured snapshots per §3's screenshot-capture constraints.

## 5. How existing products render live web frames on canvases

**Framer** — Publicly, Framer describes its canvas as literally *being* the production surface: *"what you design is what publishes... every element you create is real, semantic HTML and CSS,"* with the production site "building itself in the background" while you stay in design/canvas mode. Visually-authored animations compile down to Framer Motion code, inheriting its GPU-accelerated/spring-physics pipeline. [Framer Canvas dictionary entry](https://www.framer.com/dictionary/canvas) / [Framer animations guide (third-party)](https://framerwebsites.com/blog/framer-animations-complete-guide). **UNCONFIRMED**: Framer is closed-source, and I found no engineering blog post, conference talk, or technical writeup describing actual canvas-rendering internals (virtualization strategy, how many live component instances stay mounted, whether nested previews use real iframes). Everything beyond the marketing-level claims above is unverified.

**Onlook** (open source, `onlook-dev/onlook`) — Architecture is *"a browser that points to your localhost running the app"* — it doesn't reimplement rendering; it points a real browser surface at a real running dev server. The live app runs in a sandboxed cloud dev environment built on the **CodeSandbox SDK**, containerized via **Docker**: *"we load the code into a web container"* that *"runs and serves the code."* The canvas itself displays that running app via a plain iframe: *"the editor receives the preview link and displays it in an iFrame."* [Onlook architecture docs](https://docs.onlook.com/developers/architecture) / [Onlook README](https://github.com/onlook-dev/onlook/blob/main/README.md). Round-trip code editing works by injecting a sourcemap-like data attribute into DOM elements at build time, pointing back to the originating code location and component scope; visual edits are matched back to that location, parsed into an AST, patched, and written back to source — described as framework-agnostic in principle, currently tuned for Next.js + Tailwind. Stack: Next.js/TailwindCSS/tRPC frontend, Supabase+Drizzle for data, Bun for monorepo/runtime, AI SDK/OpenRouter/Morph Fast Apply/Relace for the AI editing loop, Freestyle for hosting. [Onlook README](https://github.com/onlook-dev/onlook/blob/main/README.md). I found no documentation of multiple simultaneous live iframes/canvas cards in Onlook — it appears architected around one active preview per project (absence noted, not confirmed either way).

**tldraw Make Real** — Detailed in §1; the core engineering point bears repeating since it's the most directly on-point precedent: tldraw's canvas is DOM/HTML-based (not `<canvas>`-raster), which is explicitly *why* it can host live iframes on the same surface as vector shapes. The specific workaround for the "iframe is a black box" export problem was to re-feed the previous iframe's actual HTML string back into the next AI prompt rather than trying to visually re-capture the iframe. The original prototype (by Sawyer Hood) put the generated result in a popup window; tldraw's shipped version moved it onto the canvas as a shape instead. [Make Real: the story so far](https://tldraw.dev/blog/make-real-the-story-so-far)

**Figma Make embedding** — Documented behavior only: pasting a Figma Make file URL into Figma Design/FigJam/Slides turns it into *"an embedded window with a preview thumbnail"*; clicking a play button switches it into an interactive mode supporting *"the same interactions as the original Make file, including scrolling, clicking, and dragging."* [Figma blog: Make embeds](https://www.figma.com/blog/introducing-figma-make-embeds/) / [Figma help: embedding Make prototypes](https://help.figma.com/hc/en-us/articles/37617790464535-Embed-a-Make-prototype-in-a-slide-deck-board-or-design-file). This **thumbnail-then-hydrate-to-live** pattern (static preview by default, live/interactive only on explicit user action) is a notable, confirmed UX precedent directly relevant to the "many live iframes on one canvas" performance question in §3. **UNCONFIRMED**: Figma has not published *how* it's implemented — whether the embed is an iframe, how the thumbnail is generated, or the sandboxing model. Treat everything about the internals as speculation.
